An agent misunderstood what I asked for and edited eleven files.

The code was not catastrophic. Some of it was arguably fine. The problem was that it landed in my working tree, interleaved with three changes I already had in progress, and separating them took longer than doing the original task myself would have.

That is the moment GemChat comes from. Not "the model is not good enough" — the model was fine. **The blast radius was wrong.**

## Reframing the question

The instinct after a bad agent run is to improve the prompt. Better instructions, more context, a stricter system message.

That is a real lever and it has a ceiling, because it is trying to make the agent always correct. It will not always be correct. Neither am I.

The better question is not "how do we make it right", it is **"what does it get to touch before a human has looked"** — and that one has an actual answer.

## Worktrees

Every orchestration run creates an isolated git worktree. Agents work there. `main` and your working tree are untouched until you say otherwise.

This is the decision the rest of the tool hangs off, and what I like about it is that it is not clever. Git already has this primitive. I did not build a sandbox, a container, an overlay filesystem or a permissions model — I used the thing that was already there for exactly this purpose.

It converts an unbounded risk into a bounded one. Worst case is now a directory you delete.

## Tiered approval, and why "confirm everything" is worse than nothing

High-risk tool calls — shell execution, file deletion — stop for explicit `y/n` confirmation. Reading a file does not. Running a test does not.

The tiering *is* the feature. A system that confirms every action trains you to press `y` without reading within about ten minutes, and then you have a confirmation prompt that confirms nothing while making everyone feel safer. That is strictly worse than no prompt at all, because it manufactures confidence.

Prompts only work if they are rare enough that you still read them.

## What multi-agent actually buys

Complex goals decompose into sub-tasks handled by specialised agents — an Architect that plans, Coders that implement, Researchers that gather context.

I want to be careful here, because "multi-agent" is doing a lot of marketing work in this industry. More agents are not smarter. Sometimes they are dumber, because context gets lost between them.

What decomposition genuinely buys is **legibility**. When a single-agent run produces the wrong answer, you have one long transcript and a shrug. When a decomposed run produces the wrong answer, you can see which stage went wrong — the plan was bad, or the plan was fine and the implementation drifted. That is debuggable. The transcript is not.

## Showing the number

Token usage is displayed, not hidden.

A fan-out across agents can spend a startling amount without any individual step looking expensive. Every stage seems reasonable; the total is not. A tool that does not surface that is not being straight with the person paying for it.

Sessions persist too — chat history, token usage, pipeline state — so an interrupted run resumes instead of evaporating.

## Rust and Ratatui

Because I wanted it to feel like a terminal tool rather than a web app in a terminal costume. Instant start, markdown and syntax highlighting inline, responsive while requests stream.

Providers are configuration — Gemini primarily, with Claude and OpenAI supported — because the model you should be using changes much faster than the harness around it, and hardcoding a provider is signing up to rewrite the tool every few months.

## The general lesson

I spent the first stretch of this project trying to make an agent more reliable. I spent the useful stretch making its mistakes cheap.

The second one is a solvable engineering problem. The first one is somebody else's research programme.
